# HS256 ou RS256? — minha comparação

Os dois algoritmos protegem o mesmo conteúdo do JWT, mas distribuem a confiança de maneiras diferentes. A pergunta central não é “qual é o melhor?”, e sim:

> Quem deve poder emitir tokens e quem deve apenas verificá-los?

## Comparação direta

| Aspecto | HS256 | RS256 |
|---|---|---|
| Tipo | HMAC simétrico | Assinatura assimétrica RSA |
| Quem assina | Qualquer componente com o segredo | Componente com a chave privada |
| Quem verifica | Componente com o mesmo segredo | Componente com a chave pública |
| O verificador pode emitir? | Sim | Não |
| Material distribuído | Segredo sensível | Chave pública |
| Operação | Mais simples | Exige ciclo de vida do par de chaves |
| Cenário comum | Backend único ou poucos serviços igualmente confiáveis | Emissor central e várias APIs consumidoras |

## Cenário 1: um único backend

```text
Backend
  |-- emite tokens
  `-- verifica tokens
```

O mesmo componente já possui as duas responsabilidades. HS256 pode ser simples e suficiente, desde que o segredo seja forte e bem protegido.

## Cenário 2: um emissor e várias APIs

```text
Serviço de identidade --assina--> token
        |
        `-- chave privada fica aqui

API A --+
API B --+-- verificam com a chave pública
API C --+
```

Com RS256, distribuir a chave pública não permite que as APIs criem tokens. Com HS256, cada API precisaria receber o mesmo segredo e ganharia poder de emissão.

## O comprometimento de uma chave

- **HS256:** o vazamento do segredo permite verificar e criar tokens. O segredo precisa ser substituído em todos os participantes.
- **RS256:** o vazamento da chave privada permite criar tokens; o vazamento da chave pública, por si só, não concede esse poder.

Em ambos os casos, a equipe precisa ter procedimentos de rotação e resposta a incidentes.

## O algoritmo não resolve tudo

Independentemente da escolha:

- aceite somente algoritmos configurados previamente;
- use chaves fortes, protegidas e separadas por finalidade;
- valide assinatura, emissor, audiência e tempos;
- envie tokens somente por TLS e trate-os como credenciais;
- planeje expiração, revogação e rotação;
- aplique autorização depois da autenticação.

RS256 não corrige claims ignoradas. HS256 não é inseguro apenas por ser simétrico. A escolha correta acompanha a arquitetura e a fronteira de confiança.

## Regra prática para minha revisão

```text
Todos que verificam também podem emitir?
  Sim -> HS256 pode fazer sentido.
  Não -> use um esquema assimétrico, como RS256.
```

Essa regra é um ponto de partida, não substitui uma análise completa dos requisitos.
