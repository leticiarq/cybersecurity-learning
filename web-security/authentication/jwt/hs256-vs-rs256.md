# HS256 vs RS256

Ambos assinam o mesmo signing input de um JWS compacto, mas criam fronteiras de confiança diferentes.

| Aspecto | HS256 | RS256 |
|---|---|---|
| Tipo de algoritmo | MAC simétrico: HMAC com SHA-256 | Assinatura assimétrica: RSASSA-PKCS1-v1_5 com SHA-256 |
| Chaves | Um segredo compartilhado | Par private key/public key |
| Assinatura | Secret key | Private key |
| Verificação | A mesma secret key | Public key correspondente |
| Distribuição | O segredo chega a cada verificador | Somente a public key é distribuída |
| Poder do verificador | Também pode criar tokens válidos | Não pode assinar sem a private key |
| Complexidade | Menor | Maior: par de chaves, publicação e rotação |
| Desempenho | Geralmente mais rápido | Geralmente mais custoso |
| Cenários comuns | Backend único ou poucos serviços igualmente confiáveis | IdP central e muitos consumidores/terceiros |
| Chave comprometida | Segredo permite assinar e verificar; deve ser substituído em todos os participantes | Private key permite falsificar; public key vazada não cria esse risco |

## Quando HS256 faz sentido

Quando um componente ou um pequeno conjunto dentro da mesma fronteira de confiança emite e verifica tokens, o segredo compartilhado pode ser simples e eficiente. A equipe ainda precisa proteger, separar e rotacionar o segredo.

Se o segredo for entregue a dez verificadores, os dez também ganham poder de emissão. Essa consequência, e não apenas desempenho, deve orientar a escolha.

## Quando RS256 faz sentido

Quando um emissor central deve ser o único capaz de assinar, mas várias APIs precisam verificar, RS256 preserva essa separação. Distribuir a public key não concede poder para criar tokens. É necessário autenticar a origem das chaves públicas, gerenciar `kid`, cache e rotação, e proteger fortemente a private key.

## Não existe vencedor universal

A decisão depende de topologia, confiança, operação e modelo de ameaça. RS256 não corrige claims mal validados; HS256 não é inseguro apenas por ser simétrico. Para ambos:

- fixe algoritmos permitidos;
- use chaves fortes e separadas por finalidade;
- valide assinatura, `iss`, `aud`, tempos e demais claims;
- use TLS e trate tokens como credenciais;
- planeje expiração, revogação e rotação.

Compare os dois diretamente na [atividade prática](practical/README.md#comparação-final).
