# HS256 — minhas anotações sobre o segredo compartilhado

## Ideia principal

**HS256** significa HMAC usando SHA-256. Ele usa a **mesma chave secreta** para criar e para verificar a terceira parte do JWT.

```text
Emissor                              Verificador
conteúdo + segredo -> HMAC           conteúdo + mesmo segredo -> HMAC
                           compara os dois resultados
```

Por usar um único segredo compartilhado, HS256 é um algoritmo **simétrico**.

## O que são SHA-256 e HMAC

SHA-256 é uma função de hash: recebe dados de qualquer tamanho e produz um resumo de 256 bits. Sozinho, o SHA-256 não prova quem calculou o resumo, porque qualquer pessoa pode executá-lo.

HMAC combina uma função de hash com uma chave secreta usando uma construção padronizada. Somente quem conhece o segredo consegue gerar o mesmo código para aquele conteúdo. Não é equivalente a apenas concatenar a chave com a mensagem.

Tecnicamente, HMAC produz um **código de autenticação de mensagem (MAC)**, não uma assinatura digital de chave pública. No formato JWS, porém, essa terceira parte recebe o nome genérico de `signature`.

## Como o token é criado

```text
base64url(header) + "." + base64url(payload)
                       |
                       v
                HMAC-SHA-256 <--- segredo
                       |
                       v
              base64url(resultado)
```

Em forma resumida:

```text
signature = HMAC-SHA-256(segredo, signing_input)
JWT = signing_input + "." + base64url(signature)
```

## Como ele é validado

O verificador separa o token, recupera as duas primeiras partes originais e calcula outro HMAC com o mesmo segredo. Se o resultado recebido e o calculado forem iguais, a integridade foi confirmada.

A comparação deve usar uma função apropriada, como `hmac.compare_digest` em Python, para evitar diferenças de tempo causadas por encerramento antecipado.

Depois disso, o sistema ainda precisa validar emissor, audiência, expiração e as demais claims. Conferir apenas o HMAC não é uma validação completa do JWT.

## A consequência mais importante

Todo componente que consegue verificar um token HS256 também possui o segredo necessário para criar outro token válido.

Se dez APIs recebem o segredo, as dez ganham tanto o poder de verificação quanto o de emissão. Essa propriedade pode ser aceitável quando todos os componentes pertencem à mesma fronteira de confiança, mas é perigosa quando verificadores não deveriam poder emitir tokens.

## Proteção do segredo

Uma pessoa que obtém um token conhece tanto o conteúdo assinado quanto o resultado do HMAC. Se o segredo for uma palavra ou uma senha fraca, ela poderá testar candidatos localmente, sem enviar novas requisições à aplicação.

Por isso, o segredo deve:

- ser gerado por um gerador criptograficamente seguro;
- ter entropia suficiente e nunca ser uma frase humana;
- ficar em um gerenciador de segredos ou mecanismo equivalente;
- ser separado por ambiente, aplicação e finalidade;
- estar disponível apenas aos componentes que realmente precisam dele;
- possuir um plano de rotação.

## Quando HS256 pode ser adequado

Ele pode ser uma escolha simples para um único backend que emite e valida seus próprios tokens ou para poucos serviços igualmente confiáveis. Quando muitos serviços ou terceiros precisam apenas verificar, [RS256](rs256.md) costuma representar melhor essa separação de responsabilidades.
